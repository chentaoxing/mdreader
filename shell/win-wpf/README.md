# shell/win-wpf —— Windows 界面壳（.NET 10 WPF）

产品名：**MD文档阅读助手**（窗口标题、程序集 Product、打开方式里的名字都是它；
exe 仍叫 `MdFileAssistant.exe`、C ABI 仍是 `mdfile_*` 前缀——这两个牵动已注册的打开方式与四平台绑定命名，要改单独提一次）。

一句话：**文件里的字节一个不由界面决定**。要不要改、改哪儿、能不能改，全部来自 `mdcore_ffi.dll`
（与 CLI、以及以后四个平台共用的同一份核心）；界面只决定**屏幕上怎么摆**。

## 构建与运行

```bash
cd shell/win-wpf
dotnet build -c Release
bin/Release/net10.0-windows/MdFileAssistant.exe 某个文件.md
```

只需要 .NET 10 SDK + Windows 桌面运行时（本机已具备），**不需要 Rust 或 MSVC**——
`mdcore_ffi.dll` 由交叉工具链产出后放进 `Native/`，构建时自动拷到 exe 同目录。
缺这个 dll 时程序会明确报一行提示，不会静默变成"什么都能干但没结果"。

## 两栏各是什么

| | |
| --- | --- |
| **左：源文件** | 等宽、不折行、不隐藏——就是那份字节。只读，永不写回，也不随阅读模式变 |
| **右：阅读视图** | 给人读的版式：段落接回整句、行长封顶、标题层级与节奏、列表悬挂缩进、引用块、代码块、表格 |

顶栏四个开关：预设（决定核心用哪套规则）、语法符号（原样 / 弱化 / 隐藏）、字号、视图（对比源文件 / 专心读）。
**这四个都只影响屏幕**，写盘的字节由核心返回的 `rendered` 决定，跟它们没有因果关系。

## 阅读视图具体做了什么

`Reading/ReadingRenderer.cs` 把 Markdown 解析成块（标题 / 段落 / 列表 / 引用 / 围栏 / 表格 / front matter），
然后：

- **接回硬换行**：源文件里为了书写方便手动断的行，在屏幕上并回一段；中文与中文之间不补空格，
  英文之间补一个空格；行尾两个空格或 `\` 视为作者本意的换行，保留。
- **行长封顶**：`MaxPageWidth = 880 × 字号系数`，标准字号约 40 个汉字一行。窗口拉宽也不会变成一堵墙。
- **标题节奏**：h1/h2 带下划线分隔，字号 25/21/18/16.5/15.5，行高 1.5–1.6 倍，`KeepWithNext` 防止标题掉在页尾。
- **列表**：按源缩进换算悬挂缩进；任务项 `[x]` 在隐藏档渲染成 ☑ / ☐。
- **表格**：隐藏档画成真表格（表头底色、隔行底色、按 `:---:` 对齐、`\|` 还原成单元格里的竖线）；
  原样与弱化档竖线属于"要留下的阅读字符"，仍按行显示。
- **代码块**：整块底色 + 等宽 + 语言标签；**引用块**：左侧竖条 + 底色；**front matter**：淡灰元信息块。
- **语法字符**：弱化档染淡灰，隐藏档不上屏（`**粗**` 直接加粗、`` `码` `` 直接以代码样式呈现）。
  链接目标不丢：隐藏档把 URL 挪到 ToolTip 与 `AutomationProperties.HelpText` 里。
- 超过 80 万字符不做富文本，降级为纯文本上屏并写明原因（几 MB 的 `FlowDocument` 会把界面拖死）。

**这些全部只在显示层。** 本类没有任何写文件的路径；`MainWindow` 的保存按钮写的是核心返回的字节，
且目标路径等于原文件时直接拒绝。

## 打开中文 Windows 老文件时（`Shell/TextDecode.cs`）

核心只吃 UTF-8，这是五平台逐字节一致的前提，不能为兼容去动它。所以转码放在这一层，
而且**只在内存里**：原文件字节不动，状态条会写明「现在读的是 UTF-8 副本」，另存出去的是一份 UTF-8 新文件。

判定顺序是「能确定才动手」，猜不出来就拒读：

1. 有 UTF-16 BOM → 按 UTF-16 解；
2. 字节里含 NUL → 直接拒（顺手堵住了「无 BOM 的 UTF-16LE 恰好是合法 UTF-8、会被当正文收下」这个洞）；
3. 严格 UTF-8 能解 → 就是 UTF-8，**字节原样交给核心，一个都不转**；
4. 都不行 → 先试 GB18030（GBK 的超集，2 字节段与 GBK 完全一致，四字节生僻字才不会解坏），再试 GBK；
   解出 NUL 或替换符超过千分之一（多半是拿二进制当中文读）就不认；
5. 全都不行 → 明说「认不出的编码我不猜，文件也没动」，两栏留空。

实测（同一份内容的四种编码各造一个文件，逐个真开一遍）：UTF-8 / GBK / UTF-16LE 三份的正文校验和
完全相同（`284810…085`），都是 6 处结构变化、正文变化 0；带 NUL 的伪 PNG 与无 BOM 的 UTF-16LE
都被干净拒读，文件未被改写。

## 逐条接受 / 拒绝

改动清单里取消勾选某条规则，即调 `mdfile_rebuild` 重建，右栏与状态条实时跟着变。
界面不参与任何排版计算——它只是把「接受哪些规则」这个决定传给核心。

## 状态条上写的是凭据，不是安慰话

```
✓ 正文内容变化 0 · 结构变化 6 处 · 校验和 284810…085 前后一致 · 收敛轮次 2 · 阅读视图的版式只在屏幕上，不写回文件
```

校验和比的是字符串（`checksum_original_str` / `checksum_str`），**不是 JSON 里的数字**——
u64 是 19 位十进制，超过 2^53，用数字比会丢末位。取不到校验和时一律按「不证明」处理，
状态条变成「不允许保存」，宁可不给存也不给一个没验过的结果。

## 「设为 .md 打开方式」按钮的实话

它只做程序能合法做的部分：在 `HKCU\Software\Classes` 注册 ProgID 并把本程序挂进 `.md` 的**打开方式列表**
（写之前 `reg export` 备份，写之后打印条目数变化，同一个按钮可撤销；撤销前会核对打开命令确实指向本程序，
不是就拒绝删）。

**Windows 10/11 的"默认应用"由 UserChoice 哈希保护，第三方程序不能合法静默改写**，
所以按钮的第二步是打开 `ms-settings:defaultapps` 让人亲手点。界面文案就照这个写，不假装已经设好。
